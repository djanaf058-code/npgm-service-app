# Spec: ИИ — человечный профи + загрузка РЭ в базу знаний

**Date:** 2026-05-26
**Status:** approved by user (brainstorming), ready for implementation
**Owner:** ВФ + Claude

## Context — почему

Жалоба: ИИ отвечает «как тупая машина» — цитирует РЭ, говорит «не нашёл / не знаю».
Разбор показал:
- Промпт уже запрещает цитировать РЭ и велит «говорить как инженер, который знает
  машину наизусть» — каркас есть.
- «Не знаю / не нашёл» идёт из (1) прямых инструкций пасовать при неуверенности +
  сообщения «Дополнительных материалов нет», и (2) **отсутствия грунта**: РЭ не
  загружены, в `manual_chunks` только FAQ из решённых тикетов.

Решения два, на уже готовой трубе RAG:
- **A. Тон/качество** — правка промпта: уверенный профи, опора на собственную
  экспертизу (горное дело/эмульсии/БВР), убрать рефлекторное «не знаю»; безопасность
  сохранить.
- **B. Загрузка РЭ** — РЭ уже лежат локально в `CODE/manuals/<ТИП>/`. Одноразовый
  скрипт парсит PDF → эмбеддит → пишет в `manual_chunks`. После этого ИИ отвечает,
  опираясь на реальные мануалы машины.

Общую базу (горное дело/химия) **не заливаем** — у Claude эти знания есть, промпт
разрешит ими пользоваться.

## Outcome

- ИИ отвечает уверенно, как старший инженер: даёт вероятную причину и что проверить
  даже без точного совпадения в базе; «не знаю» исчезает как рефлекс.
- Безопасность сохранена: при реальной нужде в физической диагностике — осознанная
  передача инженеру («нужны руки на месте»), без выдуманных опасных процедур и без
  обходов по высокому давлению/электрике/газу/тормозам.
- РЭ машин (PDF) загружены в `manual_chunks`; на вопрос про машину ретривал достаёт
  релевантные куски её мануала, и ответ становится «знающим».

## A. Persona — правки `app/src/lib/ai/prompt-builder.ts`

Оба промпта (`buildSystemPrompt`, `buildTicketReplyPrompt`) + `knowledgeBlock`:

1. `knowledgeBlock`: при пустом списке — **не печатать** «Дополнительных материалов
   нет / No additional materials». Если чанков нет, секцию «Внутренние сведения»
   опускаем целиком (ничего не подсказываем про пустоту).
2. Добавить строку: опираться на собственный инженерный опыт по эмульсионным ВВ, БВР
   и горному делу; отвечать уверенно как специалист, не как справочник.
3. Переформулировать «пасовать»:
   - вместо «если уверенно решить нельзя — скажи „нужна физическая диагностика“ и не
     выдумывай шагов» →
   - «сначала всегда дай профессиональную версию: вероятная причина + что безопасно
     проверить. Если нужна физическая работа на месте — честно скажи, что нужен
     инженер с руками, и подскажи что подготовить к приезду. Никогда не отвечай
     просто „не знаю“.»
4. Сохранить без изменений: запрет markdown/эмодзи; запрет обходов для высокого
   давления, газа/химии, электрики >50В, тормозов, аварийного останова; маркер
   `Confidence: NN` в чат-промпте (авто-эскалация остаётся).

Изменения только текстовые в промптах — логика вызовов/ретривала не трогается.

## B. Ingestion — `app/scripts/ingest-manuals.ts` (одноразовый, локальный)

Запуск: `pnpm tsx scripts/ingest-manuals.ts` из папки `app/` (резолвятся
node_modules: pdf-parse, и relative-импорт парсера/эмбеддера).

Реализация: скрипт **уже существует** из ранней сессии и подходит — переиспользуем
как есть. В нём курируемый список из 5 PDF с явными `type`+`lang` (МСЗУ ru, МЗУ en,
МСЗ en, МЗВ ru+en), батч-эмбеддинг по 96, REST-вставка, `deleteBySource` для
идемпотентности. `verified_at` не ставится намеренно — чтобы FAQ из решённых тикетов
сохраняли ×1.5-приоритет над сырым текстом мануала.

Логика (что он делает):
1. Загрузить env из `.env.local` (мини-парсер в скрипте — без зависимости dotenv):
   нужны `NEXT_PUBLIC_SUPABASE_URL`, `PRIVATE_SUPABASE_SERVICE_KEY`, `MISTRAL_API_KEY`.
2. Пройти `../../manuals/<ТИП>/*.pdf` (путь к manuals настраивается argv, дефолт
   `../../manuals`). Папки = значения `machine_type`: `МЗВ`, `МЗУ`, `МСЗ`, `МСЗУ`
   (`Буровые` пустая; `Эмульсионные_линии` — только DOCX, пропускаем).
3. Для каждого PDF:
   - `parseAndChunkPdf(path, lang)` (готовый парсер) → чанки (page, section, text);
   - язык определить **по содержимому** (доля кириллицы в выборке текста → `ru`,
     иначе `en`) — надёжнее, чем по имени файла (есть «ANFO Operational Manual.pdf»
     на английском без «eng» в имени);
   - эмбеддинг батчами по 32 (`embed(textsBatch)` Mistral);
   - перед вставкой удалить прежние чанки этого источника:
     `delete from manual_chunks where machine_type=<T> and source=<filename>`
     (идемпотентность повторного прогона);
   - вставить строки: `machine_type`, `language`, `source=<filename>`, `page`,
     `section`, `chunk_text`, `embedding`, `verified_at=now()`, `verified_by=null`
     (РЭ авторитетны).
4. Лог: по каждому файлу — тип, язык, число чанков; итог — всего файлов/чанков.

Скоуп: **только PDF**. DOCX (ТО МЗУ/МСЗ, эмульсионные линии) — отдельный шаг позже
(нужен парсер .docx, напр. mammoth).

`package.json`: добавить `"ingest:manuals": "tsx scripts/ingest-manuals.ts"`.

## Безопасность / стоимость
- Скрипт пишет в **боевую** `manual_chunks` и вызывает Mistral API (дёшево, но
  платно) → запускается **только после явного «ок»** пользователя.
- Сервис-ключ и Mistral-ключ берутся из локального `.env.local`, в репозиторий не
  попадают. Скрипт — локальный, не деплоится.

## Out of scope
- Админ-UI загрузки РЭ (сейчас файлы локальны → скрипт). Можно добавить позже.
- DOCX-парсинг.
- Заливка общих справочников по горному делу/химии (используем знания Claude).
- Изменения схемы (таблица `manual_chunks` из 0032b уже подходит).

## Verification
1. `pnpm build` — без ошибок типов/линта (правки промпта).
2. `pnpm tsx scripts/ingest-manuals.ts` (после «ок») — лог показывает обработанные
   PDF по типам, число чанков > 0; повторный прогон не плодит дубли (delete-by-source).
3. SQL-проверка: `select machine_type, language, count(*) from manual_chunks
   where source not like 'tier2_resolution:%' group by 1,2` — есть строки по МЗВ/МЗУ/
   МСЗ/МСЗУ.
4. Ручной тест в браузере: оператор/тикет по машине типа МСЗУ → ИИ в ответе опирается
   на содержание РЭ, не цитирует «страницу/раздел», не говорит «не знаю»; при запросе
   физической работы — корректно предлагает инженера.
